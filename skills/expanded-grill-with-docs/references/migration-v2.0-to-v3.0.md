# Migration: v2.0 to v3.0

V3 preserves the v2 decision-graph and document-contract architecture but replaces the interviewing policy.

## Behavioral changes

- Default grilling intensity changes from bounded 3–7 question rounds to **exhaustive maximum-coherent batching** with no fixed question cap.
- Answer burden no longer divides question value. It influences grouping, compression, and response ergonomics instead.
- Relevant coverage lenses are checked before and after major packets so missing decision categories can be discovered rather than merely traversing already-known graph nodes.
- Candidate questions may be deliberately overgenerated by parallel specialist/question-discovery lanes.
- The parent now performs explicit question sharpening, deduplication, critique, and quality gating before presentation.
- One level of clearly labeled conditional subquestions is allowed when it safely eliminates an unnecessary conversational round.
- Large packets support explicit bulk acceptance and concise numbered answers. Omitted questions always remain open.
- Recommendation rationales must name a concrete mechanism and consequence; generic "reliability/scalability/best practice" rationales fail the quality gate.

## Artifact changes

- `change-preflight.yaml` adds interview intensity and batching policy.
- `decision-graph.yaml` adds coverage state, candidate formulations, question-quality receipt, packet membership, and conditional children.
- `lane-result.yaml` adds assigned coverage lenses, interrogation angles, concrete consequences, and quality hints.
- `interview-round.md` becomes a packet template with bulk-response instructions and a question-quality receipt.
- New `question-quality.yaml` defines the machine-readable question gate.
- New `references/question-craft.md` provides question-writing standards and examples.
- New `references/coverage-lenses.md` defines the consequential coverage search space.

## Compatibility

The package name remains `expanded-grill-with-docs`. V3 is intended to overwrite v2 in place. Existing v2 graph nodes remain conceptually compatible; new fields may be populated lazily when a v2 graph is resumed.
