# shared/ria-scoring migrations

## 1.0.0 → 1.1.0: P1 coercion fix and the v2 scoring config (composite-scoring-v3 §3, §4, §13)

- **Added export `finiteOrNull`.** It is the only number-coercion path for RIA scoring. `null`, `undefined`, empty or whitespace-only strings, booleans, arrays, objects and non-finite values return `null`; finite numbers and non-empty decimal numeric strings are accepted. It never clamps.
- **Behaviour change (bug fix, applies to v1).** `weightedComposite` previously coerced a missing or `null` dimension to `0` (`Number(null) === 0`), so `weightedComposite({})` returned `F` with `assessed_weight: 100`. It now returns null scores and grades, `assessed_weight: 0` and `assessment_coverage: 0`; absent `coverage` and `confidence` are `null`, not `0`. Inputs with every dimension present score exactly as before.
- **Added** `composite-v2.config.json` (`ria.composite-v2.config@1`, `config_version` 1.0.0) with its closed schema, the loader `composite-v2-config.js`, `print-influence.js`, and the separate presentation policy `composite-v2.policy.json` (`ria.composite-v2.policy@1`, `reported_composite: "v1"`). v1 remains the reported composite; nothing reads the v2 config for the reported grade.
- Readers: no stored artifact changes shape. Consumers that relied on `Number(null) === 0` were relying on the defect.

## 1.1.0 → 1.2.0: evidence model, Integrity scoring and the v2 engine (composite-scoring-v3 §6–§10)

- **Added** `evidence-model.js` (§6, §7.2), `integrity-scoring.js` (§7.3–§7.5), and the pure engine `composite-v2.js` with its closed normalized-input contract `composite-v2.input.schema.json` (`ria.composite-v2.input@1`). The engine returns `ria.composite@2`; with the default presentation policy it is `reported: false`, `calibration_state: "uncalibrated"`.
- `implementation_sha256` now covers the engine, the input schema, the evidence model, Integrity scoring and the Integrity coverage verifier, plus the imported owner definitions. Any change to them invalidates a calibration receipt.
- Display helpers `displayPoint` / `displayLower` / `displayUpper` floor the point to one decimal and round bounds outward, so a 69.9 ceiling never renders as 70.
- Nothing here changes the reported v1 composite.

## 1.2.0 → 1.3.0: Phase 8 shadow integration (composite-scoring-v3 D6) — 2026-10-16

- `implementation_sha256` also covers the normalizers that build the engine input: `repository-improvement-assessment/scripts/composite-v2-model.js`, `architecture-improvement-intelligence/assets/architecture-evidence-binding.js` and `architecture-improvement-intelligence/assets/architecture-fitness.js`. A calibration receipt binds the normalization it was computed with. A digest computed before this change does not match, and none has been issued.
- Nothing here changes the reported v1 composite. v2 appears as `analytics.composite_v2` in RIA report data.
- **Proof receipts (§7.2, §9.2; Promotion A review 2026-10-16).** `evidentiaryState` admits a reproduction, analyzer, counter-evidence or resolution proof only through its receipt: `context.readReceipt(sha256)` must return a `ria.proof-receipt@1` (`{schema_version, kind, binding, predicate_id, ...}`) of the same kind, bound to the assessed baseline and naming the same predicate. The receipt's own `expected`, `actual`, `exit_code`, `harness_error`, `check_id`, `proposition`, `outcome` and `explains` are authoritative; a proof record that states a value its receipt does not record is inadmissible. A digest with no bytes confirms, refutes and contests nothing. New exports `containmentVerified` (containment needs a passing `prevention-check` or `runtime-guard` receipt for the same predicate) and `RECEIPT_SCHEMA`.
- **Observations resolve their source (§7.2; recheck 2026-10-17).** A strong `observation` is `observed` only when its `evidence_key` re-derives from its own path and range at the assessed binding, and `context.resolveSource(path) -> {state, lines}` finds that file in the assessed source with the cited range inside it. Without a resolver, observations stay `inferred`. `observation.confirmed` text and kind names remain insufficient on their own.
- **Structured ranges are validated (§6.1; second recheck 2026-10-17).** `codeKey` rejects a range that is not `[start, end]` with integers `1 <= start <= end` (`FAIL-EVIDENCE-RANGE`), so an observation carrying `[0,0]`, a negative, inverted or fractional range is inadmissible.
- **Missing implementation is typed apart from bad configuration (§5.3; A+C review 2026-10-18).** When a file on `IMPLEMENTATION_FILES` is absent, `loadScoringConfig` now throws `FAIL-RIA-COMPOSITE-IMPLEMENTATION-MISSING` with `missing_implementation: <relative path>`, not `FAIL-RIA-COMPOSITE-CONFIG`. RIA's report may degrade the v2 shadow on that code alone, while policy reports v1 and the named file is in fact absent. Every configuration, schema and semantic error remains `FAIL-RIA-COMPOSITE-CONFIG` and blocks.
